# T1.0a — Contrats de combat et d'IA (V1, M1 vague 0, 4 j)

Lire d'abord `docs/taches/README.md`. Première tâche de la vague 0 de M1 : elle bloque toute la
vague 1 (`docs/taches.md` §6). Indépendante de T3.2 (aucun fichier commun).
Branche conseillée : `m1-v1-contrats-combat-ia` (`./scripts/task-new.sh m1-v1-contrats-combat-ia`).

## Contexte

M1 = le clone `throne` (Nuclear Throne). La vague 0 fixe les contrats que les quatre voies
parallèles de la vague 1 implémenteront chacune dans son crate. Trois chantiers du plan
(`docs/plan-engine.md` §5) : **B5** projectiles composables et patterns (T1.1, T1.2),
**B3** statuts (T1.3), **D1** behaviors composables (T1.4), **C1** effets (T1.10). Cette tâche
crée les types de contrat, pas leurs systèmes : les tâches de vague 1 les exécutent.

Ce qui existe déjà : `crates/combat` (équipes, dégâts, santé, à terre, inventaire, grille),
`crates/effects` (crate de données pures : `Action` des power-ups, sans déclencheur ni
condition — sa doc le dit), `crates/sim_core` (contrats : `Team`, `DamageEvent`, `Modifier`,
`FrameEvents`, `Kinds`/`KindRegistry`, `RollbackSystemSet` complet). `weapons/` (2 741 lignes)
vit encore dans `crates/game` — c'est le chantier de déplacement de cette tâche.

## 1. Déplacer `weapons/` de `crates/game` vers `crates/combat`

- `crates/game/src/weapons/` → `crates/combat/src/weapons/` (`git mv`, importer réécrits).
- **Règle dure : `combat` ne doit pas dépendre de `game`** (le cycle est interdit ; `game`
  dépend déjà de `combat`). Aujourd'hui `weapons/` importe des types de `game` :
  - `crate::frame_events::FrameEvents` → en fait `sim_core::frame_events::FrameEvents` déjà
    réexporté par `game` : importer directement depuis `sim_core`.
  - `weapons/ui.rs` (142 lignes, HUD : noms d'armes, munitions — utilise `LocalPlayer` et
    `AppState`) : **reste dans `game`** (présentation). Le déplacer vers
    `crates/game/src/ui/weapon_hud.rs` (ou similaire) en réexportant ce dont il a besoin
    depuis `combat::weapons`.
  - `crate::character::visuals::VisualsAttached` (sprites d'armes attachés aux personnages,
    `mod.rs` ~645-668) : présentation → **reste dans `game`** (déplacer ce système avec
    `ui.rs`), à moins qu'un découpage plus propre apparaisse.
  - `crate::interaction::{Interactable, InteractionType}` (armes murales) : c'est une donnée
    de config. Si le code qui en a besoin (spawn des armes murales) doit rester dans
    `combat`, déplacer `Interactable`/`InteractionType` vers `sim_core` (contrat) et
    réexporter depuis `game` ; sinon, garder le spawn des armes murales dans `game` et le
    dire dans le rapport. Décider et documenter — ne pas créer de shim `game`→`combat`→`game`.
- **Preuve du déplacement** : `make test_scenarios` vert **sans** `BLESS` (61 scénarios,
  traces identiques). Un déplacement qui change une trace est un bug, pas un bless.
- `crates/game` garde un `pub use combat::weapons;` (ou une fine couche) pour ne pas
  casser les consommateurs pendant la transition ; retirer les imports devenus inutiles.
- Mettre à jour la table des crates de `docs/taches.md` §3 (ligne `combat` : + « armes » ;
  ligne `game` : « se vide au fil des jalons ») et le tableau des chantiers si besoin.

## 2. Les enums squelettes (vocabulaires de M1)

Créer les enums ci-dessous dans le crate qui les implémentera (chaque crate de vague 1 a un
seul propriétaire : pas de conflit de merge). Squelette = les variantes listées, dérivés
complets, **aucun système d'exécution** (vague 1). Les variantes viennent de `docs/taches.md`
§6 (T1.1–T1.4, T1.10) et de `docs/plan-engine.md` §4.3 : les reprendre telles quelles ; une
tâche de vague 1 peut étendre son enum **dans son crate**, jamais le renommer sans le dire
dans son rapport.

| Type | Crate | Variantes initiales |
|---|---|---|
| `ProjectileModifier` | `combat` | `Bounce(n)`, `Pierce(n)`, `Size(v)`, `Lifetime(frames)`, `Homing(force)`, `Gravity(f)` (T1.1) |
| `Pattern` | `combat` | `Aimed(count, spread, projectile)`, `Spread(…)`, `Ring(…)`, `Sequence([…])`, `Telegraph(frames)`, `Wait(frames)` (T1.2 ; forme des champs libre, se caler sur §4.3) |
| `StatusDef` | `combat` | `Burn`, `Slow`, `Stun`, `Freeze` (T1.3) |
| `Behavior` | `behaviors` (crate **à créer**) | `Chase(profile)`, `KeepDistance(min, max)`, `Strafe`, `Charge(telegraph)`, `Shoot(pattern)`, `Melee(weapon)`, `Flee`, `Wander` (T1.4) |
| `Perception` | `behaviors` | `Sight(distance)`, `Hearing(distance)` (§4.3 : `sight`, `hearing`, `needs_light`) |
| `Targeting` | `behaviors` | `Nearest(ignore: [Tag])` (T1.4) |
| `Effect { on, if, do }` | `effects` | struct `Effect { on: On, if: Vec<Condition>, do: Vec<Action> }` (champs RON `on`/`if`/`do`) ; `On` : `OnHit`, `OnKill`, `OnDamageTaken`, `OnDodge`, `OnReload`, `OnRoomClear`, `OnPickup`, `OnUse`, `OnGauge(id, Above(x))`, `Tick(n)`, `OnEvent(name)` ; `Condition` : `TargetTag(tag)`, `Carrying(id)`, `HpBelow(x)`, `HasTag(tag)`, `SquadSize(n)`, `TargetInRange(d)`, `NotHitFor(frames)` ; `Action` : réutiliser `effects::Action` existant (T1.10 étendra) |

Contraintes communes :
- Dérivés : `Clone, PartialEq, Debug, Hash` (+ `Eq, PartialOrd, Ord` si pertinent) et
  `serde::{Serialize, Deserialize}` (RON : `Fixed` en chaînes, voir `docs/conventions.md` §2).
- Un test unitaire par enum : aller-retour RON (`ron::to_string` puis `from_str`, un variant
  représentatif) — preuve que le contrat est sérialisable.
- Un test que les kinds sont enregistrés : monter l'`App` minimale du plugin et vérifier
  `Kinds::has("catégorie", "nom")` (voir §3).

## 3. Enregistrement au `KindRegistry`

Chaque plugin (`Plugin::build`) enregistre ses kinds via `app.register_kinds(...)`, comme
`BaseWeaponGamePlugin` (`crates/game/src/weapons/mod.rs`) et
`BaseCharacterGamePlugin` (`crates/game/src/character/mod.rs`) le font. Catégories (snake_case,
en `&'static str`) : `projectile_modifier`, `pattern`, `status`, `behavior`, `perception`,
`targeting`, `effect_trigger`, `effect_condition` ; noms = les noms de variantes. La convention
exacte de référence dans le contenu RON sera fixée par T1.12 (« Lint des nouveaux kinds ») ;
documenter le choix fait dans la doc du crate. **Aucun changement de `Kinds`/`KindRegistry`
dans `sim_core`** sauf besoin avéré (le dire alors dans le rapport).

## 4. Composants d'état + nouveau crate `behaviors`

- Créer `crates/behaviors` : doc de crate qui dit son contrat (vocabulaire d'IA, chantier D1,
  remplacera `behavior.rs`/`pathing.rs` de `game`), dépendances minimales
  (`sim_core`, `bevy_fixed`, `serde` ; pas de `game`), et les enums du tableau ci-dessus.
- `Statuses` (composant d'état des statuts posés : entrées, piles, expirations — forme libre,
  T1.3 le remplit) dans `combat` ; `BehaviorState` (état courant de la sélection de
  behaviors — forme libre, T1.4 le remplit) dans `behaviors`. Tous deux :
  - `#[derive(Component, Clone, PartialEq, Debug, Hash)]` (le hash sert au checksum rollback) ;
  - enregistrés en rollback + trace via `app.rollback_and_trace_component::<T>()`
    (`crates/utils/src/rollback.rs`) dans le build du plugin de leur crate. Aucun système ne
    les touche encore : le checksum ne change pas, les traces restent identiques.
- **Pas de nouveau variant de `RollbackSystemSet`** : les futurs systèmes s'inscriront dans
  les sets existants (`EnemyAI` pour behaviors, `Effects`/`Status` pour combat, voir
  `crates/sim_core/src/system_set.rs`) ; le dire dans la doc des crates. Ajouter un set
  n'est permis que si la vague 1 le demande (note dans le rapport).

  montre toujours `combat`.
