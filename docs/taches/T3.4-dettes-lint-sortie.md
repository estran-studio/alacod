# T3.4 — lot de dettes : lint, messages et finitions de contenu (1 j)

Lire d'abord `docs/taches/README.md`. Indépendant de T3.2 (aucun fichier commun).
Branche conseillée : `m0-v5-dettes-lint-sortie` (`./scripts/task-new.sh m0-v5-dettes-lint-sortie`).
Ce lot regroupe huit petites dettes d'un même thème : le lint connaît les schémas restants et
les réglages d'interface, la sortie console et l'outil `alacod-gen` deviennent propres. Chacune
est une demi-journée au plus ; toutes partagent la même branche et le même rapport.

## Contexte

- Le lint (`crates/content/src/lint.rs`, CLI `cargo run -q -p content --bin alacod --profile
  headless -- lint games/<jeu>`, cible `make lint`) refuse un contenu cassé au démarrage.
  Chaque règle a une fixture `crates/content/tests/fixtures/<erreur>/` (mini-jeu avec **un
  seul** problème) et un test dans `crates/content/tests/lint_fixtures.rs`
  (`assert_has_error(&errors, LintErrorKind::X, "extrait du message")`). Kinds :
  `BrokenReference`, `DuplicateId`, `OutOfRange`, `UnknownKind`, `Parse`. Pour les clés
  dupliquées dans un schéma RON (la `BTreeMap` écrase en silence), T2.8 a introduit
  `KeyedEntries` (voir comment `perks.ron` est désérialisé) : reprendre la même approche.
- `ui/feedback.ron` (les deux jeux) : `hit_flash { frames, color }`, `shake { frames,
  amplitude }`, `sounds { shot, reload }` — aujourd'hui chargé sans aucun lint.
- Le testbed : `games/testbed/assets/ZombieShooter/Sprites/Character/player_config.ron` a
  `starting_weapons: ["machine_gun", "pistol", "shotgun"]` **sans** `weapon_slots` (défaut 2,
  voir `games/zombies/assets/ZombieShooter/Sprites/Character/player_config.ron` qui fixe 3) :
  la troisième arme de départ dépasse le nombre d'emplacements.

## Règles à ajouter (une fixture + un test chacune)

| Fixture | Règle | Kind | Message contient |
|---|---|---|---|
| `weapons_duplicate_key` | clé dupliquée dans `weapons.ron` (ligne par schéma : `weapons` ici) | `DuplicateId` ou erreur de `KeyedEntries` | la clé |
| `melee_duplicate_key` | idem pour `melee_weapons.ron` | idem | la clé |
| `powerups_duplicate_key` | idem pour `items/powerups.ron` | idem | la clé |
| `powerup_timed_mul_non_positive` | `TimedModifier` d'un power-up avec `op: Mul` et `value <= 0` (règle sœur de `perk_mul_non_positive`, qui ne couvre que les perks) | `OutOfRange` | `value` |
| `feedback_frames_zero` | `hit_flash.frames: 0` ou `shake.frames: 0` | `OutOfRange` | `frames` |
| `feedback_amplitude_negative` | `shake.amplitude < 0` | `OutOfRange` | `amplitude` |
| `feedback_missing_sound` | un son de `ui/feedback.ron` absent du dossier d'assets (même vérification d'existence que `audio_missing_file`) | `BrokenReference` | le chemin |
| `starting_weapons_exceed_slots` | `starting_weapons.len() > weapon_slots` sur un personnage | `OutOfRange` | `weapon_slots` |

Si une règle proposée s'avère déjà couverte par le parse, garder la fixture (elle documente le
message) et le dire dans le rapport.

## D16 — `implicit_some` pour le manifeste

`game.ron` exige `mode: Some(Waves)` (T2.4) alors que le manifeste est désérialisé sans
l'extension RON `implicit_some` (`crates/content/src/manifest.rs`). Accepter `mode: Waves`
(`ron::Options` avec `implicit_some`, ou un désérialiseur dédié) ; réécrire **sans `Some(...)`** :
`games/zombies/assets/game.ron`, `games/testbed/assets/game.ron` et la fixture
`entry_mode_waves_without_waves`. Lint vert ; **aucune trace modifiée**.

## D7 — cohérence du testbed

`player_config.ron` du testbed : soit deux armes de départ, soit `weapon_slots: 3` (regarder
ce que la règle `starting_weapons_exceed_slots` rend possible, et l'effet en jeu : la troisième
arme est-elle aujourd'hui perdue ?). Si le contenu change, les traces testbed concernées se
re-blessent avec la preuve `trace-diff` (README §5) et la justification dans le commit ; sinon
aucune trace modifiée.

## Étapes

1. Créer la branche, lire `crates/content/src/lint.rs` en entier, `tests/lint_fixtures.rs` et
   la désérialisation des schémas (`crates/content/src/**`).
2. Une règle à la fois : fixture → test rouge → règle → test vert. Messages en français, même
   forme que les existants.
3. `cargo test -q --profile headless -p content` ; `make lint` (les deux jeux verts) ;
   `make gen` sans modification ; `make test_scenarios` (aucune trace ne doit changer, sauf
   D7 avec preuve).
4. Documenter les nouvelles règles dans `docs/conventions.md` §3 (tableau des règles de lint) ;
   cocher D7/D8/D9/D11/D16 dans `docs/taches/dettes.md` (colonne acceptation : « fait dans
   T3.4 ») — c'est un fichier de travail, pas le journal.
5. Vérification standard (§4), commit, merge (§6), journal.

## Critères d'acceptation

- Un test par règle, tous verts (`lint_fixtures` : 27 tests aujourd'hui, T2.8 incluse, + les
  nouveaux) ; `make lint` sans erreur sur les deux jeux ; `make gen` sans modification ;
  `make test_scenarios` vert (61 scénarios) avec les seules traces re-blessées justifiées (D7) ;
  fmt/scripts propres ; `make test_scenarios` lisible (plus de « Adding N doors »).
