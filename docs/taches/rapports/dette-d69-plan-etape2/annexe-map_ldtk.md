## 2. Question centrale : la génération lit-elle `bevy_ecs_ldtk` par nécessité ?

**Réponse en trois niveaux, tous vérifiés.**

1. **`generation/*` (3 061 lignes) ne lit `bevy_ecs_ldtk` que pour le *format* JSON**, pas pour le chargeur.
   - Imports : `bevy_ecs_ldtk::ldtk::{LdtkJson, Level, LayerInstance, FieldInstance, FieldValue, NeighbourLevel, RealEditorValue, Type}` + `EntityInstance` + trait `LdtkFields` (`from.rs:4-5`, `to.rs:5-8`, `cave.rs:6-9`, `building.rs:5`). Ces types sont de la **donnée serde** : aucune `Query`, aucun `Component`, aucun asset. Le reste est `bevy::log::debug` et `bevy::math::{IVec2,Vec2}` (compatibles ECS seul).
   - Le seul point de couplage **imposé** par le chargeur est la signature `LdtkProjectLoader { callback: Option<Box<dyn Fn(LdtkJson, Map)->LdtkJson>> }` (`loader/mod.rs:215-217`) : la génération s'exécute **dans le chargeur d'assets**, avant toute entité (c'est une fonction `LdtkJson → LdtkJson`). Elle est déterministe par graine (`RollbackRng`), jamais dans `GgrsSchedule`.
   - **Mais** : ces types viennent de `bevy_ecs_ldtk`, qui est dans `FORBIDDEN` (`check-sim-boundary.sh:27`) et tire `bevy_sprite`. Donc la génération **ne peut pas** aller dans un crate `SIM` tant que le modèle JSON est celui de `bevy_ecs_ldtk`. Deux issues : (i) la laisser côté app (**recommandé**, elle est du *chargement*) ; (ii) extraire le modèle `ldtk` (≈ 9 fichiers `src/ldtk/*`) en crate `ldtk_json` sans `bevy_sprite` dans le fork `estran-studio/bevy_ecs_ldtk` — gros chantier externe (le module utilise `bevy::prelude::Color`, `regex`, `derive_more`) pour un gain nul tant que le chargeur reste `bevy_ecs_ldtk`.
2. **`rooms.rs`, `cave.rs` (partie Ggrs), `local.rs`, `floors.rs` (système Ggrs) lisent `bevy_ecs_ldtk` par accident d'architecture, non par nécessité** :
   - Directement : `FloorSlots` (`floors.rs:119`) → `LdtkProjectHandle` ; `FloorWorldsReady` (`:152-154`) ; `FloorLevelData` (`:400-402`) → `LevelIid`, `LdtkProjectHandle`, `Assets<LdtkProject>` ; `collider.rs:19-21,51,160,215` ; `cave.rs:73` ; `add_level_components.rs:13-16` ; `plugin.rs:169,188,236`.
   - **`floor_transition_system` (Ggrs, `floors.rs:473`) lit des données LDtk non-rollback** : `GlobalTransform` des entités LDtk (`:403-430`), `Assets<LdtkProject>` (`:402,568`), `LdtkMapEntityLoadingRegistry` (`:399`), `CaveSlots` (`:398`). Elles sont **immuables après le chargement** : un snapshot pur pris une fois à `LdtkMapLoadingEvent` donne **exactement** les mêmes `Vec3` f32 (même `GlobalTransform`) et les mêmes grilles IntGrid.
   - Les `Update` de spawn (`local.rs`) ne lisent pas de type `bevy_ecs_ldtk` : ils lisent les **composants de `map`** (`PlayerSpawnConfig`, `CharacterSpawnComponent`…) posés par les `#[derive(LdtkEntity)]`, et `GlobalTransform`.
   - Conclusion : le chargeur instancie des entités, mais **tout ce que la simulation en consomme tient dans un DTO pur** (`FloorLevels`/`LevelSpawnRequest`, §5). Le registre `LdtkMapEntityLoadingRegistry` (`plugin.rs:36-78`) est déjà ce DTO pour portes/fenêtres/spawners/props.
3. **Le chargeur ne peut pas disparaître** : `scenario` joue aussi les cartes par `LdtkRoguePlugin` + `LdtkLocalGamePlugin` (`runner.rs:319-323`), en headless (sans la feature `render`). `bevy_ecs_ldtk` tire `bevy_sprite` même sans `render` ; et `scenario` charge de toute façon `AssetPlugin` (les `Assets<WeaponsConfig/CharacterConfig/…>` sont lus par les systèmes de spawn). **`scenario` ne peut donc pas être « ECS seul » à court terme** ; il restera `APP` (`check-sim-boundary.sh:30`), ce qui est cohérent avec sa classification actuelle. Court-circuiter `bevy_ecs_ldtk` (générer directement des `LevelSpawnRequest` depuis `LdtkJson`) exigerait de reproduire exactement la conversion de coordonnées (pivot, retournement y, `UseWorldTranslation`) du fork en f32 → risque de trace, 0 bénéfice mesuré.
