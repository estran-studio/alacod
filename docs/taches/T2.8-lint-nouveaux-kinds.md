# T2.8 — lint des nouveaux kinds (1 j)

Lire d'abord `docs/taches/README.md`. Dépend de T2.5 mergée (kind `PowerUp`). Branche
conseillée : `m0-v2-lint-kinds` (`./scripts/task-new.sh m0-v2-lint-kinds`).

## Contexte

- Le lint (`crates/content/src/lint.rs`, CLI `cargo run -q -p content --bin alacod --profile
  headless -- lint games/zombies`, cible `make lint`) refuse un contenu cassé au démarrage.
  Règles existantes : références (`starting_weapons`, arme d'une `WeaponLocation`…), ids
  dupliqués, valeurs hors plage (`base_health.max`, stats), kind inconnu, littéral flottant dans
  un champ `Fixed`, `firing_rate > 0`, gabarit `test:` d'une arme, `price > 0` d'un perk,
  `entry.mode: Waves` sans dossier `Wave` (T2.4, **sans fixture**), power-ups (T2.5 : id
  dupliqué, valeur hors plage, stat inconnue).
- Chaque règle a une fixture `crates/content/tests/fixtures/<erreur>/` (mini-jeu :
  `assets/game.ron` + contenu minimal avec **un seul** problème) et un test dans
  `crates/content/tests/lint_fixtures.rs` (`assert_has_error(&errors, LintErrorKind::X, "extrait
  du message")`). Copier une fixture existante (`out_of_range` par exemple) pour en faire une
  nouvelle. Kinds d'erreur : `BrokenReference`, `DuplicateId`, `OutOfRange`, `UnknownKind`,
  `Parse` (`LintErrorKind`, `crates/content/src/lint.rs`).
- Spécification : « le lint connaît `ammo_type`, `friendly_fire`, les perks (stat ids), les
  actions de power-ups ; un test par règle ».

## Règles à ajouter (une fixture + un test chacune)

| Fixture | Règle | Kind | Message contient |
|---|---|---|---|
| `entry_mode_waves_without_waves` | `entry.mode: Waves` et aucun dossier `Wave` (règle T2.4 existante) | `BrokenReference` | `entry.mode` |
| `ammo_type_empty_custom` | `ammo_type: Custom("")` (chaîne vide) sur une arme | `OutOfRange` | `ammo_type` |
| `ammo_type_unknown` | `ammo_type: Laser` : l'enum `sim_core::ammo::AmmoType` est ouvert (`Custom(String)`), donc une variante inconnue **échoue au parse** — la fixture prouve que l'erreur est rapportée (`Parse`) et lisible | `Parse` | `ammo_type` ou `Laser` |
| `friendly_fire_unknown` | valeur inconnue de `friendly_fire` (enum fermé `sim_core::damage::FriendlyFire`, lire sa doc et `docs/conventions.md` § tir ami) : erreur de parse rapportée | `Parse` | `friendly_fire` |
| `perk_no_modifiers` | perk avec `modifiers: []` | `OutOfRange` | `modifiers` |
| `perk_mul_non_positive` | `op: Mul` avec `value <= 0` (rendrait une stat nulle ou négative) | `OutOfRange` | `value` |
| `perk_unknown_stat` | `stat: Luck` inconnu (`StatId` fermé → parse) | `Parse` | `stat` ou `Luck` |
| `perk_duplicate_id` | deux perks avec le même id dans `perks.ron` (RON refuse une clé dupliquée ? vérifier ; sinon règle explicite) | `DuplicateId` ou `Parse` | l'id |
| `powerup_frames_zero` | `TimedModifier`/`CurrencyMultiplier` avec `frames: 0` | `OutOfRange` | `frames` |
| `powerup_factor_non_positive` | `CurrencyMultiplier(factor: "0.0")` | `OutOfRange` | `factor` |
| `powerup_weight_zero` | `weight: 0` | `OutOfRange` | `weight` |
| `powerup_drop_chance_out_of_range` | `drop_chance: "1.5"` (hors [0, 1]) | `OutOfRange` | `drop_chance` |
| `powerup_no_actions` | `actions: []` | `OutOfRange` | `actions` |
| `powerup_lifetime_zero` | `lifetime_frames: 0` ou `pickup_range <= 0` | `OutOfRange` | `lifetime_frames` / `pickup_range` |
| `economy_ratio_out_of_range` | `economy.ron` : `refill_price_ratio` hors [0, 1] (dette T2.3) | `OutOfRange` | `refill_price_ratio` |
| `audio_missing_file` | `audio_config` d'une arme référence un fichier son absent du dossier d'assets (dette : `weapons.ron` référence `sounds/machine-gun-reloading.ogg`, le fichier s'appelle `machine-gun-reload.ogg`) | `BrokenReference` | le chemin |

Pour `audio_missing_file` : **corriger aussi le contenu** des deux jeux (`games/*/assets/ZombieShooter/Sprites/Character/weapons.ron`,
champs `reloading`/`firing`) pour que `make lint` reste vert ; la règle vérifie l'existence du
fichier relativement à `games/<jeu>/assets/`.

Si une règle proposée s'avère déjà couverte par le parse (enum fermé), garder la fixture
(elle documente le message) et le dire dans le rapport ; si une règle est impossible sans
changer un type (`Custom("")`), l'implémenter dans `lint_weapons`.

## Étapes

1. Créer la branche, lire `crates/content/src/lint.rs` en entier et `tests/lint_fixtures.rs`.
2. Une règle à la fois : fixture → test rouge → règle → test vert. Messages en français, même
   forme que les existants (`arme « x » : champ y = z : doit …`).
3. `cargo test -q --profile headless -p content` ; `make lint` (les deux jeux verts) ;
   `make test_scenarios` (aucune trace ne doit changer : le lint ne touche pas la simulation ;
   si le renommage d'un son change une trace, c'est anormal — les sons sont hors rollback).
4. Documenter les règles dans `docs/conventions.md` §3 (tableau des règles de lint) ; ajouter
   les nouveaux kinds d'erreur si créés.
5. Vérification standard (§4), commit, merge (§6), journal.

## Critères d'acceptation

- Un test par règle, tous verts (`lint_fixtures` : 39 tests aujourd'hui + les nouveaux) ;
  `make lint` sans erreur sur les deux jeux ; aucune trace modifiée ; fmt/scripts propres.
